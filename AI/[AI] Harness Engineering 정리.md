# Harness Engineering

> OpenAI가 2025년 8월 말부터 약 5개월간, **사람이 손으로 작성한 코드 0줄**로 100만 줄 규모의 제품을 만든 실험 기록.
> 엔지니어의 일은 코드를 쓰는 것에서 **에이전트가 유용하게 일할 수 있는 환경을 설계하는 것**으로 바뀌었다.
> *- [OpenAI, Harness engineering: leveraging Codex in an agent-first world](https://openai.com/index/harness-engineering/)*

## 실험 개요

| 항목 | 수치 |
| :--- | :--- |
| 기간 | 2025년 8월 말부터 약 5개월 |
| 팀 규모 | 7명 |
| 코드 | 약 100만 줄 |
| 머지된 PR | 약 1,500개 |
| 처리량 | 엔지니어 1인당 하루 3.5 PR |

- 빈 git 저장소에서 시작, 초기 스캐폴딩부터 Codex CLI(GPT-5)가 생성
- `AGENTS.md` 자체도 Codex가 작성
- 범위: 제품 코드와 테스트, CI 설정, 릴리스 툴링, 내부 개발 도구, 문서, 평가 하네스, 리뷰 코멘트, 저장소 관리 스크립트, 프로덕션 대시보드 정의 파일까지

## 핵심 원칙: 에이전트 가독성(Agent Legibility)

> 에이전트가 실행 중 컨텍스트에서 접근할 수 없는 것은 **사실상 존재하지 않는 것**이다.

- 저장소를 사람이 아니라 **Codex가 읽기 좋게** 최적화하는 것을 1순위로 둠
- 기술 선택도 "지루한(boring)" 쪽을 선호 — 기준은 **조합 가능성, API 안정성, 학습 데이터에 얼마나 등장하는가**
    - 예: 범용 `p-limit` 패키지 대신 `map-with-concurrency` 헬퍼를 직접 구현 (테스트 커버리지 100% + OpenTelemetry 연동)

## 1. 저장소 지식을 단일 진실 공급원으로

- 거대한 단일 지침 파일 대신, **구조화된 `docs/` 디렉터리**를 system of record로 사용
- `AGENTS.md`는 **약 100줄짜리 목차** 역할만 담당
- 문서 구성
    - 검증 상태가 표기된 설계 문서
    - 아키텍처 문서 (도메인·패키지 계층 맵 포함)
    - 제품 도메인과 아키텍처 계층에 **등급을 매기는 품질 문서**
    - 진행 로그가 포함된 실행 계획 — 저장소에 함께 커밋
- **전용 린터와 CI 잡**이 지식 베이스가 최신인지, 상호 링크되어 있는지, 구조가 올바른지 검증
- **"doc-gardening" 에이전트**가 주기적으로 낡은 문서를 스캔

## 2. 애플리케이션 가독성 높이기

- git worktree 단위로 앱을 독립 부팅 가능하게 구성
- **Chrome DevTools Protocol**을 에이전트 런타임에 연결 → DOM 스냅샷, 스크린샷 스킬 제공
- 로그·메트릭까지 **완전히 격리된 환경**을 에이전트에게 제공
    - 로그는 **LogQL**, 메트릭은 **PromQL**로 질의
- 덕분에 이런 프롬프트가 가능해짐
    - "서비스 startup이 800ms 이내에 끝나도록 해줘"
    - "이 4개 핵심 유저 journey에서 어떤 span도 2초를 넘지 않게 해줘"
- 단일 Codex 실행이 **6시간 이상** 지속되기도 함

## 3. 아키텍처와 취향(Taste)을 기계적으로 강제

- 각 비즈니스 도메인 내부에 **고정된 계층**을 두고 의존 방향을 엄격히 검증

```
Types → Config → Repo → Service → Runtime → UI
```

- 인증, 커넥터, 텔레메트리, 피처 플래그 같은 **횡단 관심사는 Providers라는 단일 인터페이스**로만 진입
- 강제 수단: **커스텀 린터(당연히 Codex가 생성)와 구조적 테스트**
- 정적으로 강제하는 "취향" 불변식
    - 구조화된 로깅
    - 스키마·타입 네이밍 규칙
    - 파일 크기 제한
    - 플랫폼별 신뢰성 요구사항

## 4. 처리량이 머지 철학을 바꾼다

- 에이전트 산출량이 사람의 리뷰 용량을 압도하므로, **차단(prevention)보다 교정(correction)** 을 우선
- 저장소는 **블로킹 머지 게이트를 최소화**해서 운영
- PR은 짧게 살아있다가 빠르게 머지
- 테스트 flake는 무기한 블로킹하지 않고 **재실행으로 처리**하는 경우가 많음

### 리뷰도 에이전트끼리

- Codex가 로컬에서 셀프 리뷰 → 추가 에이전트 리뷰를 요청 → **모든 에이전트 리뷰어가 만족할 때까지 반복**
- 사람의 PR 리뷰는 **선택 사항**이 되었고, 리뷰 노력의 대부분이 agent-to-agent로 이동

## 5. 자율성 수준의 상승

프롬프트 하나로 기능 하나를 end-to-end 처리:

검증 → 버그 재현 → 영상 녹화 → 수정 구현 → 앱 테스트 → PR 생성 → 피드백 대응 → 빌드 실패 수정 → **머지까지**

## 6. 엔트로피와 가비지 컬렉션

- **"골든 원칙(golden principles)"** 을 저장소에 기계적 규칙으로 인코딩
    - "직접 만든 헬퍼보다 공유 유틸리티 패키지를 우선하라"
    - "데이터를 'YOLO 방식'으로 탐색하지 말고, 경계를 검증하거나 타입이 있는 SDK에 의존하라"
- **백그라운드 Codex 태스크**가 주기적으로 이탈을 스캔하고, 품질 등급을 갱신하고, 타겟 리팩터링 PR을 자동으로 열어줌
- 이전에는 **매주 금요일(주의 20%)을 "AI slop" 정리**에 썼는데, 이 과정을 자동화한 것

## 남은 과제 (원문 기준)

- 장기적인 아키텍처 일관성을 어떻게 유지할 것인가
- 사람의 판단을 어떻게 인코딩해야 복리로 누적되는가

## 덧붙임: Martin Fowler의 하네스 프레임워크

> ⚠️ 아래는 OpenAI 원문 내용이 **아니라**, martinfowler.com에 실린 별도 글의 정리 프레임워크입니다. 위 사례를 일반화해서 볼 때 유용해서 함께 적어둡니다.
> *- [Harness engineering for coding agent users](https://martinfowler.com/articles/harness-engineering.html)*

**Agent = Model + Harness** — 모델을 제외한 나머지 전부가 하네스.

| 축 | 구분 | 설명 |
| :--- | :--- | :--- |
| 시점 | **가이드(피드포워드)** | 행동 전에 방향 제시 (설계 문서, 아키텍처 규칙) |
| | **센서(피드백)** | 행동 후 검증·교정 (테스트, 린터, 리뷰) |
| 실행 방식 | **계산형** | 결정론적·빠름 (린터, 타입 체커) |
| | **추론형** | 의미론적·느리고 비결정론적 (AI 리뷰, LLM-as-judge) |

**3가지 하네스 범주**

1. **유지보수성** — 코드 구조·스타일. 가장 성숙하지만 "설계 과잉" 같은 고차원 문제는 못 잡음
2. **아키텍처 피트니스** — 계층 의존성, 성능 요구사항, 로깅 표준
3. **동작(행동)** — 기능적 정확성. 가장 미성숙. AI 생성 테스트 품질이 낮아 "승인된 픽스처" 같은 패턴을 실험 중

**배치 원칙 (왼쪽에서 품질 확보)** — 커밋 전에는 LSP·빠른 린터, 통합 파이프라인에서는 뮤테이션 테스트·아키텍처 리뷰, 이후에는 죽은 코드 탐지·SLO 감시.

사람 개발자는 이미 암묵적 하네스를 갖고 있음 — 사회적 책임감, 300줄 함수에 대한 미적 거부감, "여긴 이렇게 안 한다"는 직관. 좋은 하네스는 사람을 배제하는 게 아니라 **사람의 개입을 가장 중요한 지점으로 집중**시킨다.

## 정리

- Harness Engineering = "에이전트에게 무엇을 시킬까"가 아니라 **"에이전트가 스스로 좋은 결정을 내리는 환경을 어떻게 설계할까"**
- 실무 축 3개
    1. **지식을 저장소 안에 기계가 읽을 수 있게** 넣고, 린터와 CI로 최신성을 강제
    2. **아키텍처와 취향을 커스텀 린터·구조적 테스트로 정적 강제** (`Types → Config → Repo → Service → Runtime → UI`)
    3. **처리량에 맞춰 머지·리뷰 철학을 교정 중심으로** 바꾸고, 엔트로피 정리는 백그라운드 에이전트에 위임
- 개인 프로젝트에 바로 옮길 만한 것: `AGENTS.md`를 100줄 목차로 유지 + `docs/`를 실제 근거로 삼기, 지키고 싶은 규칙은 문장이 아니라 **린터로** 표현하기
